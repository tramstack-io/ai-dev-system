SECTION 02 / PROBLEMS

Current problems.

  1. Problem 01

    Email fragmentation

    Same patterns, parallel implementations.

    Buttons, headers, and modules exist in slightly-different copies across Responsys and Dynamic Yield templates. Older campaign-based builds carry inconsistencies in responsiveness, spacing, and dark mode — each refactor a manual pass.

    Impact Slower iteration. Inconsistent rendering. Growing QA load.

  2. Problem 02

    Amplience & SFCC

    Two systems, one boundary, no map.

    Content types have grown organically. How frontend templates connect to PDP, PLP, slots, and ISML isn't documented in one place. New work begins with time lost understanding existing structures.

    Impact Time lost understanding existing structures. Duplicate types. Brittle templates.

  3. Problem 03

    Documentation falls behind delivery

    Knowledge lives in code, not in a shared system.

  4. Problem 04

    Inconsistent design handoff

    Unclear specifications across spacing, states, and tokens — with no shared source between Figma and code.

  5. Problem 05

    Repetitive, fragmented workflows

    Campaigns and content updates carry their own steps. Effort accumulates and delivery slows.

SECTION 03 / THE SYSTEM

works in practice.

STAGE 01 — THINK

Claude Code

Structured reasoning before any code is written. Scope, constraints, edge cases, naming, and the shape of the change — all decided upfront.

Example prompt
Plan refactor
— list shared modules across Responsys templates
— group by reuse pattern
— propose partials structure
— flag dark-mode & spacing

In practice Before opening the code editor; scope a refactor, draft a content-type plan, write the brief for a campaign template.

STAGE 02 — BUILD

Cursor

Execution against the plan. Frontend components across SFCC, Amplience, Dynamic Yield, and Email Design — always reviewed, not automated.

Workflow
Build component
— follow design.md or specific-pattern.md
— reuse existing patterns
— propose change
— wait for review
— commit on approval

In practice Cursor works the plan inside the repo. Each change is reviewed step-by-step before it lands on a branch or site.

SECTION 03 / THE SYSTEM

design.md —
one file that bridges
design and code.

One file in the repo. Tokens, spacing, and component contracts in plain text. Designers, engineers, and AI tools all read the same source.

→ Tokens stay in lockstep with Figma.
→ Components carry their own contract.
→ Drift becomes a diff, not a debate.

design.md
## Tokens
color.brand.primary = #4A0E37
color.surface.warm = #F5F2ED
space.grid = 8
radius.button = 0

## Components
Button/Primary
— must support keyboard focus ring
— min hit target: 44px
— track: cta_click(name, position)

SECTION 03 / THE SYSTEM

Claude Skills replace memory
with enforcement.

A skill is a reusable instruction set Claude follows on every task. Standards enforced at write time — not caught in review.

“Don't trust me to remember.
Make the system check.”

Accessibility

WCAG checks on every component. Contrast, focus order, labelling, keyboard reachability — flagged at write time.

Performance

Budget-aware by default. Image sizing, lazy loading, and weight thresholds surfaced before changes are reviewed.

Naming

Consistent naming and structure. A single pattern across components and campaigns — readable to engineering, marketing, and analytics.

Conventions

House style, without thinking. Folder structure, naming, commit notes — boring, but expensive when ignored.

SECTION 03 / THE SYSTEM

Used in tiers —
reviewed, not automated.

Beginner

Use Orientation, naming suggestions, copy editing.

Control No write access. Step-by-step validation.

Intermediate

Use Bounded edits in a single component. Reviewed changes, one at a time.

Control Branch only. Controlled updates. Tests must pass.

Advanced

Use Multi-file audits, structured refactors with clear scope.

Control Plan reviewed first. Manual sign-off on every change.

SECTION 04 / USE CASES

Use cases.

Use case 01
Email design system refactor(s)
Problem
A legacy backlog of campaign templates needs refactor. Modules live in parallel copies across Responsys.
Current pain
Inconsistent rendering, dark mode handling, and spacing across templates. Single changes touch many files.
Solution
Map templates against design.md, identify inconsistencies, refactor into a shared module set — reviewed, not automated.
Outcome
Faster updates. Reduced QA issues. A scalable component system across the email programme.
Use case 02
Amplience template audit
Problem
Content types and Handlebars templates have accumulated. Legacy template drift is unmapped.
Current pain
No audit visibility. Old templates stay live because no one has time to confirm they're unused.
Solution
A structured audit of templates and usage — mapping relationships between content types and site output. Reviewed, not automated.
Outcome
A current map of the Amplience & SFCC seam — the artefact we never had time to write by hand.
Use case 03
Proactive frontend performance
Problem
Performance is measured episodically. Issues across PDP, PLP, and content blocks surface late.
Current pain
Slow issue identification. Regressions live for days before anyone notices, making root cause harder to isolate.
Solution
Routine checks across templates and variants. Potential light integration with staging URLs. Advisory first — reviewed, not automated.
Outcome
Visibility. Faster issue identification. Proactive improvements — not a quarterly project.

SECTION 06 / RISK

Where AI is used —
and where it is not.

Used for

  • Reasoning and planning before code.
  • Bounded code generation in a branch.
  • Audits, documentation, scoped refactors.
  • Standards enforcement via Claude Skills.
  • Supporting structured technical outputs (e.g. briefs, component descriptions)

Not used for

  • Production deploys.
  • Secrets, credentials, customer data.
  • Unattended writes to main.
  • Decisions about people or scope.
  • Anything outside standard review and approval processes.
